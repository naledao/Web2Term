# 第 26 项：跨应用任务连续性

用户只需布置一个目标，例如“从网页取得报表，用表格应用整理并保存，再回到浏览器核对”。模型可以自行发现应用、打开资源、定位窗口并切换操作对象。同一目标的任务 ID、代次和原始要求保持一致，每一步继续使用原有工具和真实结果。

本项保留现有系统提示词、助手角色、终端／文件／后台工具的 JSON 协议和确认规则。computer 的工具说明增加历史线索的含义，工具结果补充 `task_continuity`；不要求用户预先选择应用或窗口，也不新增执行模式、规划模型或强制计划格式。

## 连续性记录

`TaskContinuityService` 依据已校验执行器的结构化结果，更新 `AutonomousTask.continuity`，通过原任务存储保存。记录包含机器、来源步骤、采集时间和证据类型：

| 记录 | 来源与用途 | 数量上限 |
| --- | --- | --- |
| 应用 | `list_apps` 实际返回的 app_id、名称和可执行文件路径，帮助后续重新发现；索引不保存启动授权 | 32 |
| 窗口 | 已校验窗口发现、聚焦回执、窗口观察与输入后观察；以 HWND、PID、进程启动时间、线程和窗口类组成完整身份，关联最新返回的 window_id、标题和应用路径 | 48 |
| 资源 | `read_files` 成功读取的源文件快照，或 `open` 的真实打开回执；保存规范路径／URL、证据类型、来源步骤，读取快照附字节数及 SHA-256 | 64 |
| 接续记录 | 观察窗口、确认聚焦、派发打开／启动、未确认结果和文件读取之间的步骤关联 | 32 |

摘要随 computer 结果和关联的终端／文件结果回传，最多提供最近 6 个应用、8 个窗口、8 个资源和 6 条接续记录，附索引总数。摘要固定标记 `history_only=true`、`requires_fresh_observation=true`、`goal_verified=false`。

这些标记约束历史索引本身；当前动作在 `data` 内实际返回的新观察仍按原规则使用，不要求为了历史标记重复采集。

`last_window` 表示最近操作或观察留下的历史线索，不保证当前前台仍是该窗口。打开／启动仅得到派发结果时，不能据此选择一个候选窗口作为业务对象；聚焦／输入结果未确认且没有新观察时，也不维持“已知当前目标”的假设。输入结果不确定但操作后观察已成功时，保留该次真实观察用于下一步判断。

## 应用与窗口如何衔接

应用发现／启动引用按工具注册实例、会话、平台、任务 ID、代次和 helper 实例隔离。同一目标先发现应用 A，再发现应用 B，不会仅因查询切换而丢弃仍在有效目录中的 A 引用。其他目标、会话和工具注册不能借用这些引用；分页引用还必须来自本任务相同查询的真实返回结果。目录刷新或 helper 更换后须重新发现。

窗口索引按完整进程／窗口身份合并重新发现的记录。新查询返回同一真实窗口的新 window_id 时更新该线索；即使 HWND 相同，只要进程启动时间等身份变化，也作为不同窗口保存。不会仅按标题或 PID 合并，更不会按窗口顺序随意选择第一个。

原窗口目录仍执行有效期、原生身份复核和新查询撤销旧引用的规则。历史索引不会延长 window_id、控件、观察、截图或启动引用的有效期。模型返回先前应用时，应根据线索重新 `list_windows`，按需要 `focus_window`，再 `observe` 并使用新观察中的目标。

软件在 `focus_window`、`open`、`launch_app`、`list_windows` 和 `inspect_interactions` 派发前撤销该任务的旧输入观察；原命令真正进入执行时也撤销旧观察，不通过命令关键词猜测它是否影响 GUI。待发送截图文件仍可按原步骤交付，但不能继续用作输入授权。每次动作依旧明确提供目标，软件不默认操作历史中的“上一个窗口”。

## 文件与产物线索

文件准备过程只在实际读取并成功准备快照后记录源路径、字节数和 SHA-256。它记录原文件路径，上传暂存路径、重命名附件或 DeepSeek 的 `.txt` 兼容别名不会成为产物路径。部分读取失败只登记成功项；附件交付重试复用已准备数据，不重新读取或重复登记。

`open` 成功只登记 `open-dispatched`，未知派发保留 `open-unconfirmed`。这些证据不等于内容已加载、文件由本目标生成或处理完成。任意终端输出、文件名猜测和模型自述不会被解析成产物。生成、下载、保存等结果可在后续真实读取／打开时进入索引，文件内容、保存正确性和整体业务目标仍需模型继续验证。

## 取消、存储与实现边界

连续性更新须匹配当前目标、代次、机器和正在执行的步骤，执行结果迟到后不能改写新目标。新目标从独立索引开始；重启保留历史，但任务继续按原规则标记为中断，不恢复窗口、应用、截图或控件授权。持久化字段有严格校验和数量上限；保存失败停止自动推进，不重放已经派发的动作。

本项复用原 TaskCoordinator、TaskProgression、命令／文件执行器和发送确认机制。结果忙碌时保留原结果及当时的连续性摘要，仅重试交付，不重复聚焦、打开、输入或读取文件。[第 27 项](deepseek-computer-use-desktop-coordination.md)已接入全局桌面租约，交接时撤销所有旧输入观察；完整全入口发送队列由第 29 项继续实现。

## 构建与用户测试

交付标准为“构建通过，等待测试”。智能体不执行测试、不启动 Electron／helper，不操作真实应用、文件或后台进程。

由用户运行的合成回归用例：

```powershell
node --test tests/task-continuity.test.mjs tests/task-tool-collaboration.test.mjs tests/windows-app-catalog.test.mjs tests/windows-window-catalog.test.mjs tests/windows-observation.test.mjs tests/task-progression.test.mjs
```

用例覆盖同目标浏览器→表格→浏览器接续、真实资源路径、窗口引用刷新与句柄复用、跨任务／注册引用隔离、旧观察撤销、部分文件读取与别名、附件重试、迟到结果、索引上限和重启不恢复授权。所有桌面、窗口、文件和发送行为均为合成数据或受控替身。

真实流程只通过 `npm run dev` 启动，由用户测试。建议布置一个涉及浏览器、文件管理器、编辑器／表格应用的连续目标，检查无需预选窗口、原始目标不变、每次操作明确目标、回到旧应用后重新观察、资源路径正确；再检查多窗口同名、应用退出重开、手动切换焦点、读取失败、发送忙碌、换目标和重启。工具发送成功与窗口打开均不能代替业务结果核对。
