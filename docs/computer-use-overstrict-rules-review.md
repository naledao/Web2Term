# Computer Use 过严判定排查与修复清单

审查日期：2026-10-27。审查对象：当前工作区的 TypeScript 主进程、Windows 原生 helper、已有测试源码和功能说明。审查开始时工作区已有未提交修改，以当时工作区代码作为修复前基线；下面的过严条件描述该基线，当前处理结果见状态栏及修复记录。

## 1. 主要结论

最值得修复的是以下三类问题：

1. 把整个窗口、整棵控件树或全局事件的变化，等同于当前操作目标失效。
2. 把 UIA 信息缺失、合理的重复操作和正常等待，等同于不可操作或任务没有进展。
3. 不同层采用不同的有效期、复核标准和恢复条件，导致模型拿到结果后又被另一层拒绝。

建议保留任务归属、窗口真实身份、原生输入路由、坐标转换、取消和执行回执校验，围绕具体动作缩小其余判定范围。不能通过放宽这些规则自动重放已经可能生效的输入。

优先级：P1 为常见流程中的直接阻断或明显规则冲突；P2 为特定控件、应用或恢复场景中的兼容性问题。下表的“待修复”只表示尚未改代码。逐项分析中的行号指审查时的代码位置，修改后可能移动。

## 3. 逐项分析

### CU-01：窗口观察本身要求界面完全静止

- **代码位置**：`native/computer-use/windows/ObservationBinding.cs:65`、`:91`、`:347`；`WindowsObservationStateBackend.cs:71`；`WindowLifetimeMonitor.cs:28`。
- **当前条件**：窗口的 `CaptureDifference` 沿用完整 `Difference`，包含焦点、popup 和事件修订；状态读取期间修订变化也直接抛出 `stale_observation`。
- **使用场景**：模型只想看一下正在加载的文档或更新中的列表；采集期间恰好出现受监听的状态、位置或焦点事件，即使窗口身份和图像几何都没变，结果仍可能无法发布。
- **过严原因**：读取一个动态界面与授权一次输入，需要的证据不同。事件修订变化只能证明发生了某类变化，不能直接证明截图不能阅读。微软也建议将事件订阅限定到关心的范围，且提醒事件并不完整。[事件文档](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-eventsforclients)
- **建议**：读取时严格核对来源身份、边界、DPI和图像尺寸；内容或内部焦点变化用非原子快照/局限信息表达。实际输入再进行相应的实时目标检查。
- **验收**：动态内容期间仍能返回真实截图；窗口身份替换或尺寸/DPI变化时仍拒绝发布错误映射。

### CU-02：坐标滚动被整图散列和悬停变化阻断

- **代码位置**：`native/computer-use/windows/Scroll.cs:57`、`:81`；`ObservationBinding.cs:155`。
- **当前条件**：滚动使用通用 `WithCurrentObservation`；坐标路径会重新编码整图并比较 SHA-256，移动鼠标后还会再检查一次。
- **使用场景**：页面有独立转圈动画，或者鼠标进入列表使一行变色；滚动目标仍然正确，但实际滚轮尚未发出就因 `image_changed` 被拒绝。
- **过严原因**：整图一致性覆盖了与滚动落点和路由无关的像素。现有测试源码 `tests/native-app-catalog/ScrollTests.cs:94` 明确把悬停变化写成阻断案例；这里只读了测试，未运行。
- **建议**：首次检查目标局部及来源几何，悬停后检查窗口、命中区域与滚轮路由；不要再要求旧整图与悬停后整图一致。保留实际滚轮接收数和后观察。
- **验收**：无关动画和目标区域的普通悬停高亮不阻止滚动；落点被另一窗口覆盖、路由无法确认时仍阻止。

### CU-03：拖拽在正常悬停效果出现后被拒绝

- **代码位置**：`native/computer-use/windows/Drag.cs:73`、`:87`、`:93`、`:119`。
- **当前条件**：拖拽多次调用通用观察复核，包含整图散列；最后一次发生在鼠标移到起点之后、按钮按下之前。
- **使用场景**：PPT或绘图软件在对象上显示边框/控制点，文件列表在起点处显示悬停高亮。
- **过严原因**：这些像素变化是正常指针交互的一部分。当前拖拽持有期间已经允许内部正常内容变化，但开始之前的要求仍过于宽泛。
- **建议**：开始前验证目标局部、来源和完整路径；到达起点后以实时命中、前台、几何及输入占用判断能否按下。不能把陌生遮挡当成普通悬停忽略。
- **验收**：悬停显示控制点后可以开始拖拽；起点被其他窗口覆盖则不按下；中途取消仍释放本次按钮。

### CU-04：窗口级快捷键仍依赖整张截图或完整旧树

- **代码位置**：`native/computer-use/windows/ObservationBinding.cs:228`、`:141`、`:218`；`PressKey.cs:90`。
- **当前条件**：`WithCurrentWindowKey` 先用 `Purpose=inspect` 调通用 `Validate`；图片会比较整图，无图时会比较整棵树。
- **使用场景**：动态网页里按 Escape，自动保存状态变化时按 Ctrl+S，自绘应用里用 Tab 导航。
- **过严原因**：窗口级按键已在后端核对真实前台和键盘路由。屏幕上与该按键无关的变化，不应额外要求整图/整树相同。当前已去掉 UIA readiness 门槛，但整图门槛仍存在。
- **建议**：窗口级按键采用专用来源/原生键盘路由检查；明确指定 `element_id` 的按键继续核对该控件。
- **验收**：窗口身份与键盘路由正确时，普通动态内容不妨碍快捷键；焦点跑到别的应用时不得发送。

### CU-05：只读坐标复核与实际点击标准不一致

- **代码位置**：`native/computer-use/windows/ObservationBinding.cs:289`、`:382`；`src/main/windows-observation.ts:344`。
- **当前条件**：真实窗口坐标点击已经使用 `WithCurrentWindowPoint`；公共 `validate_observation` 仍进入更严格的通用 `Validate`，可能比较整图、焦点和修订。
- **使用场景**：模型习惯先复核再点击；同一个落点直接点击本来可通过，先复核却因无关变化被判失效，继而触发补图和新一轮判断。
- **过严原因**：一个本用于帮助决策的只读工具，采用了与执行入口不同的拒绝标准。文档也容易让模型误以为它是每次点击的必要前置步骤。
- **建议**：复核根据用途使用与实际动作一致的来源、局部或控件检查，并清楚说明复核结果不是可重复使用的输入许可。调用复核不得消费输入。
- **验收**：无关动画下，窗口坐标复核与点击的来源判断一致；实际派发前仍重新核对原生窗口和落点。

### CU-06：目标控件和祖先的所有可变属性必须完全相同

- **代码位置**：`native/computer-use/windows/ObservationBinding.cs:187`、`:191`、`:211`；`ControlTree.cs:47`。
- **当前条件**：控件指纹包含名称、focused、selected、patterns 等，`SameAncestors` 对每层祖先重复比较完整指纹；实时原始属性也做完整相等比较。
- **使用场景**：编辑器标题出现“未保存”标记、父容器选中态更新，目标按钮的身份和落点却没有变化。
- **过严原因**：祖先应主要证明身份和包含关系。把祖先的展示名称、选中态和焦点态也当作操作目标身份，会把正常状态更新放大成整个定位失效。
- **建议**：祖先核对稳定身份和真实祖先关系；目标按动作核对必要属性。名称、选择态发生语义变化时需要重新判断的控件，保留更细粒度约束。
- **验收**：无关祖先名称变化可通过；控件换成另一个同名对象、移出原祖先或被禁用仍拒绝。

### CU-07：指针操作不必要地绑定 UIA 键盘焦点

- **代码位置**：`native/computer-use/windows/ObservationBinding.cs:213`；`WindowsObservationStateBackend.cs:24`。
- **当前条件**：普通 `element_id` 指针路径拒绝 UIA 焦点不可用或前后变化；原生菜单已有例外。这里并非要求被点击按钮本身已经获得焦点，而是要求窗口的 UIA 焦点可读且稳定。
- **使用场景**：按钮可见、启用且可在物理位置命中，但其应用无法稳定报告 UIA 键盘焦点。
- **过严原因**：点击通常正是为了改变焦点。对于指针动作，真实前台、身份、可见性和命中位置比旧 UIA 键盘焦点更直接。
- **建议**：指针定位不再依赖无关的 UIA 键盘焦点；文字输入和指定控件按键继续要求正确的键盘目标。
- **验收**：焦点信息缺失不妨碍可见按钮点击；输入文字仍不能流向未确认目标。

### CU-08：综合属性完整性成为所有动作的共同开关

- **代码位置**：`native/computer-use/windows/ControlTree.cs:152`、`:55`；`ObservationBinding.cs:211`；`src/main/windows-observation.ts:294`。
- **当前条件**：`properties_complete` 综合名称、焦点、密码属性、边界等多个字段；多条输入路径先要求它为 true。
- **使用场景**：一个控件可用、位置和身份可确认，但某项辅助属性不可读，整个控件因此不能操作。
- **过严原因**：不同动作需要的属性不同。微软允许 UIA 提供方不实现某些属性，客户端需要处理 unsupported，而不是把所有属性一律视为必需。[属性文档](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-propertiesforclients)
- **建议**：区分读取完整性与具体动作所需条件；保留未知值，不伪造 true/false。文字/密码保护所需的敏感属性不能借此放宽。
- **验收**：缺少无关属性不阻止指针动作；身份、落点或必要敏感属性缺失仍明确报错。

### CU-09：文字输入没有窗口级兼容入口

- **代码位置**：`src/main/windows-observation.ts:292`；`native/computer-use/windows/TypeText.cs:75`；`src/shared/windows-type-text.ts`。
- **当前条件**：必须指定当前 UIA 焦点控件；目标需要为 edit/document 或具有 Value pattern。
- **使用场景**：自绘编辑区、某些嵌入式网页编辑器或终端提供的 UIA 信息不足，虽然真实键盘光标已经在输入区，`type_text` 仍无法使用。具体应用/版本需用户验收。
- **过严原因**：现有 `press_key` 已允许无 `element_id` 的窗口级键盘操作，文字输入却无对应兼容路径。
- **建议**：保留严格控件输入，补充明确的窗口级 insert 入口，核对最近窗口观察、真实前台/焦点路由、用户干扰和输入占用；返回内容未验证事实。不要自动把一次未知结果改走另一条路径重输。
- **验收**：缺少 UIA 编辑控件的窗口可在已核对键盘路由时输入；切换前台、取消及部分输入时及时停止。

### CU-10：replace 仅支持 UIA Value

- **代码位置**：`native/computer-use/windows/TypeText.cs:84`；`tests/native-app-catalog/TypeTextTests.cs:62`。
- **当前条件**：没有可写 Value 就在执行前拒绝 replace，不提供清空/全选再输入路径。
- **使用场景**：编辑器可以通过键盘选中和替换，却没有可写 Value 模式。模型有时可以自行分解为 Ctrl+A 和 insert，但单次 replace 的兼容性仍不足。
- **过严原因**：保护“不能在不确定写入后自动回退”是合理的；在任何写入开始之前，把已明确请求的替换永久限定为一种能力则可以改善。
- **建议**：只在已确认未开始写入、目标为可编辑控件且替换范围明确时选择键盘替换策略；否则返回可执行的分步替换指导。不能对文档级 Ctrl+A 范围作无依据假设。
- **验收**：无 Value 的受支持编辑目标可以受控替换；Value 已调用但结果未知时不补做全选和重输。

### CU-11：两分钟引用与最长十分钟回传延迟冲突

- **代码位置**：`src/main/windows-observation.ts:199`；`native/computer-use/windows/ObservationBinding.cs:102`；`WindowCatalog.cs:138`；`src/shared/computer-progress.ts:39`；`src/main/task-progression.ts:305`。
- **当前条件**：观察及窗口批次约两分钟失效；结果发送前可按设置等待 0—600 秒。
- **使用场景**：用户设置 180 秒延迟；截图尚未交给模型，引用已经过期。仅延长观察 TTL 也无法绕过窗口批次的另一道过期检查。
- **过严原因**：这是可以从配置和代码直接推导的规则冲突。模型等待、上传和思考还会进一步压缩实际可用时间。
- **建议**：区分引用的存活时间与内容新鲜度；旧引用需实时核对身份/几何后重新取证。统一主进程、helper 和窗口目录的期限策略，避免只改一层。实际输入不能只凭延长 TTL 放行。
- **验收**：超过两分钟的合法交付延迟后可以继续定位当前真实目标；同句柄新窗口、尺寸/DPI变更仍不能复用旧坐标。

### CU-12：持久对话框与瞬时菜单统一三十秒失效

- **代码位置**：`native/computer-use/windows/WindowInteractions.cs:95`；`WindowCatalog.cs:139`。
- **当前条件**：`inspect_interactions` 的 dialog、owned_window 和 menu 引用共同使用 `min(采集前时间+30秒, 窗口批次到期时间)`。
- **使用场景**：模型阅读“另存为”文件名与路径、处理较长提示时，对话框仍开着但引用已失效。
- **过严原因**：菜单短暂存在与普通对话框持续存在的生命周期不同，不适合共享短期限。
- **建议**：菜单继续严格核对当前菜单上下文；对话框及普通 owned window 使用稳定身份、owner链与持续有效的引用策略。
- **验收**：三十秒后仍存在的对话框可重新核对后操作；旧菜单关闭或重开后不能沿用旧上下文。

### CU-13：任何 owned popup 都被视为阻断输入

- **代码位置**：`native/computer-use/windows/WindowsObservationStateBackend.cs:29`、`:56`；`WindowsClickBackend.cs:35`。
- **当前条件**：可见 owner 后代窗口被加入 popups，控件输入 readiness 要求 `popups.Count == 0`；拖拽也对可见 last-active popup 作阻断。
- **使用场景**：非模态工具面板、浮动属性窗持续显示，但主文档仍可操作。
- **过严原因**：Windows owner关系不等价于模态阻塞。当前窗口坐标点击已有较宽松路径，所以并非所有点击都会被这一条挡住。
- **建议**：结合目标 enabled、真实前台/命中、菜单状态和具体模态事实判断；仅在弹窗实际阻断目标或覆盖落点时禁止动作。
- **验收**：非模态面板不阻止主窗口的无关操作；主窗口被模态框禁用时仍拒绝向主窗口输入。

### CU-14：按键协议遗漏常用 OEM 标点键

- **代码位置**：`src/shared/windows-press-key.ts:7`、`:19`；`native/computer-use/windows/PressKey.cs:11`、`:23`。
- **当前条件**：允许字母、数字和一组命名按键；`-`、`[`、`]`、`/`、反引号及主键盘加号等缺少可表达名称。
- **使用场景**：缩小视图、切换缩进、注释代码、切换集成终端等快捷键。具体快捷键行为依应用及键盘布局而定。
- **过严原因**：这是常用按键能力缺口。数字小键盘 Add/Subtract 并不总能代替主键盘相应按键。Windows 明确定义相关 OEM 虚拟键。[虚拟键文档](https://learn.microsoft.com/en-us/windows/win32/inputdev/virtual-key-codes)
- **建议**：扩充受控命名键，如 Minus、Equal、LeftBracket、RightBracket、Slash、Backquote，并保持 TS/C# 解析一致及布局说明；无需开放任意 VK 或脚本。
- **验收**：常用标点组合可以表达；错误别名、空组合和安全注意序列仍拒绝。

### CU-15：滚轮路由要求焦点 HWND 与命中 HWND 完全一致

- **代码位置**：`native/computer-use/windows/WindowsScrollBackend.cs:21`；`Scroll.cs:14`。
- **当前条件**：垂直且采用 mouse-position 路由时直接允许；其他分支要求 `gui.Focus == hit`，水平滚轮同样如此。
- **使用场景**：鼠标命中滚动容器，但键盘焦点在其编辑子窗口；应用通过正常父链处理滚轮。
- **过严原因**：微软说明滚轮消息可由 DefWindowProc 沿父链传播，严格 HWND 相等覆盖不了合法容器关系。由此推断当前规则可能误拦截；不能由该文档反推任意同进程窗口都可接收。[垂直滚轮](https://learn.microsoft.com/en-us/windows/win32/inputdev/wm-mousewheel)、[水平滚轮](https://learn.microsoft.com/en-us/windows/win32/inputdev/wm-mousehwheel)
- **建议**：支持可证明的同一目标内父子路由，或明确提供 UIA Scroll 策略；两个无关分栏仍不能仅凭同进程放行。
- **验收**：同一滚动区域中的父子焦点可操作；相邻分栏存在路由歧义时继续拒绝。

### CU-16：正常业务等待受三十秒和连续超时双重限制

- **代码位置**：`src/shared/windows-wait.ts:37`；`src/shared/computer-progress.ts:15`、`:19`；`src/main/task-progress-guard.ts:77`。
- **当前条件**：桌面条件一次最多30秒；任务设置中的 waitTimeoutMs 默认一小时，无法放大这道参数上限。`wait_timeout` 与执行器故障超时共用默认3次的计数，成功执行的其他步骤会重置该计数。
- **使用场景**：模型连续等待大文件打开或导出，三次检查都未到条件；业务可能还在正常工作，任务却先停止。并非所有等待都会必然在90秒停止，中间成功动作和实际期限会影响计数。
- **过严原因**：条件尚未满足与输入执行器失联是不同事实。
- **建议**：桌面等待受配置和任务剩余预算约束，允许较长的单次有界等待；把正常条件超时与执行器故障分别累计。保留总期限、退避和取消。
- **验收**：可等待超过30秒的正常加载；真实 helper 超时仍触发对应限制；等待不重复启动/提交原业务。

### CU-17：控件可用性等待要求全树完整

- **代码位置**：`native/computer-use/windows/WaitFor.cs:20`；`src/shared/windows-wait.ts:52`。
- **当前条件**：即使已经找到一个完整、可见且启用的目标，只要 `tree.complete == false`，`control_available` 就返回 unavailable；选择器只有精确 name 和可选 role。
- **使用场景**：复杂页面因无关分支、名称截断或深度预算导致整树不完整；目标“保存”按钮却已读到。
- **过严原因**：当前全局选择器确实不能在部分树上证明唯一性，不能简单删除检查；问题是没有办法在更小、完整的相关范围内表达等待。虚拟化控件也说明“未出现在树里”不是“整个UI不存在”。[虚拟化文档](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-workingwithvirtualizeditems)
- **建议**：增加受控的存在性等待或目标/区域限定方式，区分“有可用匹配”与“唯一可操作目标”；不把非唯一的存在证据作为点击许可。
- **验收**：部分树上可证明目标已经存在；需要唯一性时仍拒绝多个同名目标，不能默认选择第一个。

### CU-18：附加观察失败抹掉先前条件命中的事实

- **代码位置**：`src/main/windows-observation.ts:245`、`:258`。
- **当前条件**：轮询命中后还必须成功补采观察；text/control 条件还需在新树里再次命中，否则改为 changed/observation_failed，并报 wait_failed。
- **使用场景**：短暂的“完成”提示已被采样到，但结束后消失；或者命中时UIA可读，随后补采失败。
- **过严原因**：不应把“在某时刻观察到满足”与“现在仍持续满足”混成一个事实。后者对随后输入有意义，但不能改写历史采样。
- **建议**：分别返回采样命中、采样时间、后观察和当前是否仍确认；不同等待语义明确区分瞬时事件与持续状态。
- **验收**：保留已命中的事实和后采失败信息；下一次输入仍要独立确认当前目标可操作。

### CU-19：第二次非只读动作统一阻断

- **代码位置**：`src/main/task-progress-guard.ts:18`、`:36`；`tests/computer-progress.test.mjs:67`。
- **当前条件**：相同语义动作在同一证据 epoch 内 `repeat >= 2` 就 blocked；设置的默认4次是之后的硬停止阈值，不是允许执行4次。
- **使用场景**：连续方向键移动光标、均质列表继续滚动、再次激活同一窗口；这些操作不一定立刻改变当前摘要。
- **过严原因**：发送/支付/启动类动作防重复与导航类动作的合理重复需要不同处理。当前动作指纹相等不等于重复副作用。
- **建议**：按动作语义分级；导航允许有限重复，提交类动作继续核对后状态。真实请求ID/步骤令牌的重复派发去重继续保留。
- **验收**：导航可在预算内重复；同一发送按钮在无新证据时仍阻断；旧请求重传不再次执行。

### CU-20：不同来源的相同只读结果共同累计硬停止

- **代码位置**：`src/main/task-progress-guard.ts:67`、`:85`、`:97`；`src/shared/computer-progress.ts:18`。
- **当前条件**：窗口/应用列表和观察都可产生摘要；对任何已见来源再次读到相同值，就递增同一个 unchangedObservations；默认达到6次停止。
- **使用场景**：发现窗口、读取控件、查看截图、再次核对窗口身份，业务状态本就应该保持稳定。
- **过严原因**：相同状态是核对的正常结果，特别是定位、恢复和条件等待阶段。跨来源累加还会把不同目的的读取混成一次无进展循环。
- **建议**：按来源和动作目的追踪同一循环；相同观察先提供诊断信号，只有重复且无有效下一步的循环才考虑停止。总步骤与总时限继续约束。
- **验收**：正常核对不因多类只读结果相同而过早终止；持续无意义轮询仍受到限制。

### CU-21：所有诊断一律进入恢复预算

- **代码位置**：`src/shared/computer-diagnostics.ts:59`、`:82`；`src/main/task-coordinator.ts:477`；`src/main/task-progress-guard.ts:40`、`:95`。
- **当前条件**：包括 partial_observation 在内的任何 diagnosis 都会设置 recovering；后续步骤消费同一恢复预算，默认12步，直到新的证据变化等条件清除。
- **使用场景**：一个应用的 UIA 始终不完整，但截图路线可用；模型只是收到能力局限说明，仍可能进入恢复计数。
- **过严原因**：部分可读、建议补充核对、确切执行失败和副作用未知是不同严重程度。诊断文本存在不应成为异常恢复的统一开关。
- **建议**：诊断显式区分信息提示、可恢复失败和未知副作用；只有需要恢复的类型消费恢复预算。成功的有效观察可结束相应恢复阶段，不要求无关像素必须变化。
- **验收**：部分树配合有效截图可继续正常推进；持续失败且无可用证据时仍达到恢复上限。

### CU-22：恢复白名单禁止必要诊断与准备动作

- **代码位置**：`src/main/task-progression.ts:89`；`src/shared/computer-diagnostics.ts:93`；`src/main/task-coordinator.ts:481`。
- **当前条件**：requiresObservation 时仅允许 list_apps/list_windows/observe；inspect_interactions、validate_observation、wait_for、focus_window 等都不能通过该入口。
- **使用场景**：截图因窗口最小化失败，需要先恢复；前一步打开了弹窗，需要先发现关联窗口；业务仍在加载，需要只读等待状态。
- **过严原因**：门槛要求先观察，却禁止为完成观察所需的部分操作，形成绕路甚至死路。该限制是 computer 请求入口的限制，不代表原有 read_files/command 必然都被这里禁用。
- **建议**：按真实副作用和恢复原因控制；允许当前任务的只读诊断/等待，并允许有真实窗口身份的恢复/激活准备。未知提交动作继续禁止重放，只有新的适用观察才能解除输入门槛。
- **验收**：可先发现弹窗或恢复窗口再观察；不能直接重做未知结果的点击、输入、保存或启动。

### CU-23：完成证据被无关全局操作和两分钟年龄作废

- **代码位置**：`src/main/task-completion.ts:15`、`:140`；`src/main/task-coordinator.ts:509`。
- **当前条件**：多种非只读动作递增全局 completion revision；observation/command 证据必须与当前 revision 相同，且不超过2分钟。focus_window 也不在只读集合中。
- **使用场景**：先核对文档A，再切换到表格B完成另一部分，A的证据因全局代次变化过时；模型整理较长报告时，证据又可能单纯因时间过期。
- **过严原因**：证据新鲜度应联系它所证明的对象及后续可能改变该对象的操作。全局最后一次操作不一定与已经核对的产物有关。
- **建议**：按对象/资源保留证据有效性；文件继续核对真实字节，界面或命令证据说明其采样时刻及相关后续变更。必要时补充当前状态，不重做已完成业务。适当统一交付延迟与证据期限。
- **验收**：跨应用多项任务可以引用各自真实证据完成报告；实际改写某产物后，其旧证据不能继续证明新内容。

## 6. 建议修复顺序与用户验收

按 CU-01 → CU-23 逐项处理。共用底层逻辑一次修改影响多个项目时，在各项状态中明确关联，避免重复放宽。每一批代码改动完成后执行 `npm run build`；构建通过只代表可编译打包，真实行为仍等待用户测试。

| 验收组 | 用户执行场景 | 应观察的结果 |
| --- | --- | --- |
| 动态界面 | 页面持续变化时截图、滚动、按键；画布悬停后拖动 | 返回真实观察；无关变化不阻断目标；错误窗口/遮挡仍被拒绝 |
| UIA兼容 | 部分UIA、自绘编辑区、浮动非模态面板、无Value编辑控件 | 选择实际受支持输入策略，局限和未验证内容明确返回 |
| 时序 | 回传延迟180秒、持久对话框等待45秒、加载超过30秒 | 引用可重新核对，正常等待不混算执行器故障 |
| 导航与恢复 | 连续方向键、同一列表滚动、发现弹窗、恢复最小化窗口 | 有界导航可以继续；未知提交不重放；必要诊断可执行 |
| 完成核对 | 文档A和表格B分别完成，最后统一报告 | 证据关联各自对象；改写后旧证据作废；无关切窗不作废已核对文件 |
