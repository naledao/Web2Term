# ChatGPT 专注会话：编辑并重新发送

ChatGPT 的纯文字用户消息下方增加「编辑消息」铅笔按钮。点击后原位编辑，
Enter 重新发送、Shift+Enter 换行、Esc 或「取消」放弃修改。
编辑期间保留底部输入框原有草稿；新回复确认后切换到新分支。

当前仅接入 ChatGPT 的纯文字消息。带附件的消息和其它平台继续使用原来的交互。

## 实测依据

用户运行的 `chatgpt-edit-2026-10-23T14-35-02-142Z-644.log`：

- 第 246、251 行：编辑按钮所在回合的 `data-turn-key` 与编辑框一致。
- 第 328、333 行：原网页 Enter 产生编辑输入事件；第 343、346、349 行的按钮点击、
  表单提交之后才出现真正的 `POST /backend-api/f/conversation`。
- 第 350 行：重发使用 `action: next`，新的用户消息 ID，父消息仍是第一轮的助手回复。
- 第 353 行：当前 DOM 从三轮变为第一轮与新的第二轮。第 396、405 行：刷新后接口仍返回新分支。

此版本网页的历史接口返回 `messages` 和 `current_node`，并非旧的 `mapping` 对象。
因此探针的 `graphResponses: 0` 不代表没有采到历史；判断依据是前后历史消息列表、DOM 和发送请求。
四个流式连接均记录为 canceled，没有拿到完整流式响应正文，不将它们算成流式正文已覆盖。

## 实现边界

页面操作通过实测的 `data-turn-key` 回合、`aria-label="编辑消息"` 编辑框及原生表单完成。
优先用本地保存的助手 sourceMessageId 定位对应用户回合，无回复时只接受唯一且文字一致的回合。
历史编辑框与底部输入框隔离；原网页存在草稿、正在生成、上传或等待问题时不会覆盖、重发。
注入长提示词的消息气泡可能折叠并带有「显示更多」，不能用它的可见预览核对完整原文。
定位到消息后先打开原生编辑框，读取完整原文完成核对，再写入修改。
提交前核对完整输入，等待编辑框稳定至少 180ms，并重新读取网页当前的编辑框和提交按钮。
原生表单在未修改时本就可以提交，按钮可用不代表 ProseMirror / React 已处理新文字。
提交后被动读取这次原生请求的正文，在内存中比对新文字与旧文字，并要求请求中的用户消息 ID
等于原位置新气泡的 ID、编辑表单消失，才确认成功。不依赖气泡的折叠预览。

每次只点击一次原生提交按钮；新用户 ID 和实际提交正文必须同时匹配才能确认成功。
页面确认携带本次操作 token，经主进程再次确认后才替换专注回合。
结果不确定时保留本地修改并提示先核对原始视图，不自动重试。

被替代的专注回合标记 `supersededBy`，旧本地消息 ID 由新回合记录并从专注视图隐藏；
不删除消息或执行记录。新分支保存后重启仍保留这些关系。
替换过程过滤旧助手消息，避免把暂时露出的历史回复接到新回合或执行为新指令。

## 用户运行的检查

智能体不运行测试或 Electron。用户可在项目根目录执行这些离线检查：

```powershell
node --test tests/focus-edit.test.mjs tests/focus-chat.test.mjs tests/focus-page.test.mjs
```

检查覆盖实际页面编辑方法的定位、单次提交、异步输入状态同步、请求正文和新 ID 同时确认、
旧正文误发送、仅 DOM 改动、草稿保护、取消、超时、重复操作隔离、主进程消息归属、
被动监听只注册一次且操作结束释放、旧回复过滤和分支关系持久化。

真实验收只用以下命令启动正常应用：

```powershell
npm run dev
```

1. 在 ChatGPT 专注会话中完成三轮纯文字问答。
2. 编辑第二轮，修改后取消，确认旧消息、回复和第三轮仍在。
3. 再编辑第二轮，用 Enter 重新发送；确认第一轮保留，第二轮变为新回复，旧第三轮不再显示。
4. 再用按钮修改一次，检查 Shift+Enter 换行、中文输入法确认字词不误发送、Esc 取消。
5. 重启应用、重新打开同一会话，确认新分支保留；继续追问仍能正常发送。
6. 底部留有草稿时编辑并重发，确认底部草稿未丢失；模型生成或等待命令确认时编辑按钮应禁用。
7. 检查浅色、深色及窄窗口：编辑框不越界，键盘焦点可见，失败时修改内容保留。

正常使用的元数据日志仍在 `%TEMP%\gpt-login-diag\chatgpt-focus-ui-*.log`，
增加 `edit-request` / `edit-page` / `edit-outcome`，不记录编辑正文。
`edit-page` 只记录 prepare / locate / open / verify / insert / submit / request / confirm 阶段、
固定失败原因、回合数量、是否通过回复 ID 定位及文字长度，便于区分定位失败、原文不一致、
页面仍使用旧脚本和提交结果不确定。

`2026-10-23T15-17-51-037Z-20612-1.log` 第 4 行 `inputLength: 7` 表明新文字已进入主进程，
第 9 行 `originalMatches: true`、`submitted: true` 和 `new-user-confirmed` 只表明找对原文并出现新 ID。
旧版没有比对实际请求正文，不能根据该日志断言新文字已发出；该确认缺口已补上。

新增诊断字段：`draftMatches`、`editorStableReads`、`settleMs` 记录编辑框稳定情况；
`requestBodyReadable`、`requestTextMatches`、`requestOriginalMatches`、`requestCount` 记录实际请求比对结果。
带原有分隔标记时还记录 `requestUserLength`。不写出请求正文、提示词、Cookie、请求头或文件内容。
监听器每个分区只安装一次，仅在用户主动编辑期间读取对应视图、会话和已实测接口的纯文字请求，
不增加请求，不取消、重放或改写请求，不占用上传所用的 debugger。

- `request-matched`：实际请求正文与本次修改匹配；仍需新气泡的消息 ID 匹配才能成功。
- `request-original`：实际请求仍是旧正文；不会确认本地替换，也不自动重发。
- `request-mismatch`：请求可读取，但正文既不匹配新文字，也不匹配旧文字。
- `request-body-unavailable` / `request-schema-unavailable`：请求无法可靠读取或结构变化，保留修改并提示核对。
- `request-not-observed`：没有观测到可归属的原生提交请求，不能仅凭新 ID 报成功。

构建通过不代表真实交互已验证，当前交付状态为「构建通过，等待用户测试」。
