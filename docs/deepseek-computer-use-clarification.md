# 第 39 项：必要澄清与任务内授权

交付状态：**构建通过，等待测试**。已编写离线用例，未运行测试，未启动 Electron／helper，未访问真实 DeepSeek 会话或操作桌面。

## 实现效果

AI 继续按原系统提示词、原确认规则和现有 `questions` 协议工作。computer use 只补充工具使用说明：先用实际工具解决可核实的问题；确实缺少无法从环境取得的用户信息、需要超出原目标的决定，或遇到系统／站点强制人类步骤时，才说明阻塞原因并提出必要问题。没有逐应用、逐窗口或逐动作的新确认流程。

例如，AI 能自行发现报表位置、读取文件、定位窗口和核对结果，就直接推进；环境无法确定收件人、用户没有授权的范围变化，或实际登录／验证码步骤，则用原问题弹窗收集回答。登录等步骤由用户在真实界面完成并报告状态，不通过问题索取密码或验证码正文。

必要性及自然语言授权的含义仍由当前模型依据原确认规则判断。主进程保存真实的问题和用户回答，校验归属、交付与执行状态，不使用“允许”“确认”等关键词生成全局批准，也不替模型扩大授权范围。用户拒绝某条路径、补充“只保存本地，不发送”等限制，都会原样保留为原任务的补充要求。客户端开关、运行上限、执行模式和原确认规则不会因回答而改变。

## 沿用的提问格式

```json
{
  "type": "questions",
  "questions": [
    {
      "question": "无法从当前环境确定收件人。本次是否只生成文件并保存本地？",
      "options": ["只生成并保存，不发送", "我补充收件人后再决定"],
      "placeholder": "也可以填写其他限制或必要信息"
    }
  ]
}
```

模型侧 JSON 格式、问题数量／选项规则及现有多题一次回答流程不变。问题归属、页面代次和任务代次是软件传输元数据，模型不填写这些字段。

## 问题与原任务绑定

DeepSeek 的实时问题在清除当前回复等待状态前捕获真实发送来源。网页报告问题编号、原目标发送编号、当前路径、提示词代次和主进程签发的页面代次；主进程再次核对 DeepSeek 域名、真实页面路径及当前会话，再关联 session、task、generation 和 machine 上下文。

`question-history` 仍只用于保存历史 JSON，不能将当前任务切到等待用户。手动历史回放也不会创建当前任务的授权请求。原任务的“查看并回答原问题”只重开已记录且仍有效的问题，不向模型发送新消息，不生成新批准。

任务问题的弹窗还带有主进程签发的 `taskContext`。回答、关闭、重开操作会校验完整任务归属与独立问题标识；即使不同会话复用了相同消息编号，旧弹窗也不能回答或关闭新任务的问题。网页模型的 JSON 无法提供或覆盖这个上下文。

同一问题重复报告不会重复等待、重复取消或再次占用授权。迟到的真实回答可保存到它实际回答的问题；如果同一原任务已经有更新的问题，新问题仍继续等待，不会被旧回答解除。更换目标、切换会话、提示词／页面代次变化后的旧回答不能成为新目标的授权。

## 等待和交付状态

| 状态 | 含义 | 任务行为 |
| --- | --- | --- |
| `pending` | 必要问题已记录，尚未回答 | 保留原目标，停止自动工具派发及自动结果发送 |
| `sending` | 用户提交回答，等待网页真实发送确认 | 先持久化状态，不能把正在提交当成同意 |
| `answered` | 原会话确认实际发送了匹配回答 | 完整回答加入同一任务的 `inputs`，允许模型继续判断，但不改变执行权限 |
| `dismissed` | 用户在本地关闭问题弹窗 | 不发送取消反馈、不视为允许或拒绝；原任务仍等待，可重新打开 |
| `uncertain` | 回答提交结果或确认事件未知 | 保留上下文并阻止重复提交；先核对原对话，必要时关闭问题后显式恢复原任务 |
| `cancelled` | 问题被更新问题、停止任务或替换上下文撤销 | 保留历史，不授予任何后续执行资格 |

已知发送前失败，如输入框忙、写入失败、页面未就绪，允许用户重试。网页仅返回 `ok`、但没有收到匹配的真实用户发送事件时，仍记录为未知；不能因此追加要求、解除等待或认定授权。迟到的实际确认按原问题归属处理。

等待期间不签发 computer 步骤令牌，终端／文件任务的自动接纳及后台结果自动回传同样受原任务等待状态限制。旧排队步骤和发送重试取消，迟到执行／交付回执仍可补充历史，不重放动作。必要澄清没有解决时，任务不能被标记为完成。等待用户的时间沿用原等待阶段的预算规则，不计作模型或工具执行时间。

任务进入等待后释放原桌面 owner；真正仍在执行的 permit 继续保留到执行器退出。因此，用户填写信息、操作登录界面或完成必要人工步骤时，不会被旧 AI 桌面 watch 误判成另一轮人工接管。独立后台进程、日志及监控继续保持原生命周期。

## 回答后接续

正常回答保留同一任务编号和任务代次，原始要求不变，完整回答作为补充约束持久化。旧步骤令牌失效，并签发新令牌；之前的输入观察失效，下一步需要新 `observe`，不能沿用人工操作前的坐标或控件。

回答确认时清除旧活动步骤的执行资格，旧执行器迟到的观察只补历史，不能清除回答后的观察屏障。模型依据新状态、原目标和新增限制继续选择工具；回答“已登录”只是用户提供的状态，后续仍需观察真实页面，不能把它当成业务完成。

若回答发送未知，界面提供“核对后恢复原任务”，沿用第 32 项的显式恢复流程。恢复仍要求原会话、实际页面状态、运行预算和真实新消息确认，创建新任务代次并重新观察。恢复摘要将旧问题和答案标为 `history_only=true`、`grants_permissions=false`；未确认回答仍需核对，不自动重发或扩大为批准。

客户端重启会把正在提交的回答改记未知，并把原任务设为中断。恢复历史不恢复弹窗授权、旧令牌、旧观察或发送缓冲。

## 数据与展示

`AutonomousTask.clarifications` 保存有界问题历史、实际来源、状态和已确认回答。最多保留最近 32 个问题，并明确标记历史裁剪；所有已确认的完整回答仍保存在原任务输入中。严格解析器核对问题状态、来源、回答与真实任务输入的一致性。

工具结果增加 `task_clarification_context`，只提供有裁剪标识的问题／回答摘要，不提供权限。原命令／文件工具的上下文还保留当前客户端执行模式；这些都是结果数据，不改写系统提示词。任务摘要展示等待原因、发送未知、重新打开问题入口和最近实际回答，不显示“已批准所有操作”一类推断状态。
