# 系统提示词优化调研：完成标记与回复协议

日期：2026-10-29。基线：v0.1.196，提交 `84756dc`。本文件记录实际日志、代码核对、外部资料和候选方案。用户确认后已将方案接入代码，实施范围见第 9 节；模型效果等待用户测试。

## 结论

优先优化固定回复协议、普通问答示例和协议的持续传递。保留当前环境、工具说明的按需注入，避免每轮重新发送完整提示词。

这次故障发生在首条消息已经完整注入之后，不能归因为“没有注入”“只发了短锚点”或“上下文已经太长”。可以确认的是：前两次回答没有被识别为完成；追问后的第三次回答被成功识别。截图中模型对自身行为的解释只能用来发现措辞歧义，不能证明其内部推理过程。

## 2. 当前实现的关键问题

### 2.1 “完成语义”和“完成格式”没有充分分离

`src/shared/types.ts` 的【任务完成】已经要求所有任务以标记开头，并写有“纯对话完整回答即完成”。问题不是缺少这句话，而是仍留有解释空间：模型可能把“完整回答即完成”理解为不需要另发执行任务的结束标记。截图中的回复正好展示了这种解释。

建议直接说明：目标是否完成是语义判断；首行标记是软件读取的结束信号。直接回答、网页检索和机器操作使用相同的结束格式，是否使用工具不改变结束格式。

### 2.2 工具路由比最终回答有更多明确示例

当前【需要执行时】、【判断与确认】和【工具目录】包含 JSON 示例，但普通问答没有“用户输入—正确最终回答”的示例。角色名称也是“终端助手”。这些可能强化执行任务的语境，是设计层面的推断，仍需对比测试。

建议保留终端能力，但将角色表述为协助完成当前用户目标；工具是完成目标的方法之一。增加直接回答、工具结果已核对后的最终回答两种正例。

### 2.3 按任务注入遇到漏标记时缺少纠偏机会

`src/main/injected/send-interceptor.js` 的普通发送、附件、编辑路径均以 `taskPromptInjected` 控制完整前缀注入。原任务未结束时，后续用户消息不会再次发送前缀。

`src/shared/prompt-injection.ts` 的无变化锚点只有“此前注入的约定继续有效”。即使扩充这个锚点，仍不能单独解决截图问题：原任务没有结束，锚点也未必会随下一条消息发出。

因此应将“固定回复约定”和“环境/工具内容的增量注入”分开处理。前者随真实用户消息轻量传递，后者继续使用现有账本；不要把轻量提醒当成新任务，也不要重置步骤令牌、待回答问题或执行状态。

### 2.4 当前格式违约没有覆盖漏完成标记

`src/main/session-runtime.ts` 的 `onParseFailed` 才会增加 `violations`。普通自然语言回答没有首行标记时，页面报告 `completed: false`，不会进入该路径。现有“违约后提醒/完整刷新”的机制对本例不起作用。

建议先记录“已结束但未携带完成标记的普通回复”这一事实，而不是直接判定任务完成或强行重试。需要结合正在执行、等待用户、后台依赖和取消状态，才能判断是否值得在下一次用户发送时补充格式提醒。

### 2.5 提示词是用户消息前缀

界面称为“系统提示词”，实际发送路径是 `state.prefix + USER_TEXT_SENTINEL + text`，并不是设置第三方模型 API 的 system 角色。不能靠把文字改为“最高优先级”就获得 API 消息层级或强制输出格式的能力。

### 2.6 示例与分段账本存在兼容点

`splitPromptSections()` 当前将任意单独成行的 `【…】` 识别为分段标题，没有跳过代码围栏或示例区。直接加入包含独立 `【任务完成】` 行的示例，会产生额外的同名分段，影响指纹、提醒和增量内容。

接入示例前，需要使分段器识别代码围栏/示例区域，或者在构建阶段传递明确的分段结构。回归检查应保证示例完整保留在所属协议分段中。

## 3. 一手资料及适用范围

- [Anthropic：提示词最佳实践](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)：明确输出要求、解释规则用途、提供相关且多样的正例。这里借鉴方法，不把 Claude 上的经验当成 DeepSeek 网页端的效果保证。
- [DeepSeek：JSON Output](https://api-docs.deepseek.com/guides/json_mode/)：格式要求配合示例；API 的 JSON 模式还需要专门设置 `response_format`。当前项目使用网页文本协议，不能把 API 的格式能力等同于网页端保证。
- [Liu 等：Lost in the Middle](https://arxiv.org/abs/2307.03172)：信息位置会影响长上下文检索表现。该研究不是对本项目完成标记的实测；这里只据此把规则位置纳入评估，不将长度或位置断言为本次原因。
- [Anthropic：定义成功标准与评估](https://platform.claude.com/docs/en/test-and-evaluate/develop-tests)：先设定可测目标，使用贴近实际分布的任务及边界场景比较候选方案。

旧版 DeepSeek-R1 的模型专属建议不能直接当作当前 DeepSeek 网页模型的通用规则。本次候选不依赖特定模型的隐藏推理提示或 API 采样参数。

## 4. 建议的提示词结构

| 层 | 内容 | 传递方式 |
| --- | --- | --- |
| 固定回复协议 | 完成、工具、提问、等待的区别；最终回答格式；必要的正例 | 完整注入时保留全部，后续真实用户消息携带短版 |
| 任务处理规则 | 直接回答/查询资料/操作机器的路由；确认、验证、失败处理 | 继续按分段变化更新 |
| 环境与工具信息 | 当前 shell、目录、搜索能力、工具开关和具体参数 | 继续按需、按变化注入；保留完整动作参数语义 |
| 用户补充 | 当前任务的偏好与约束 | 与环境和软件回复协议明确区分 |

网页、文件和命令输出中的内容按资料处理，避免把资料中的指令误当成软件回复协议。用户确实需要改变软件结束协议时，应与客户端识别方式同步设计；当前“用户补充优先”的宽泛表述需要评估其边界，但截图中补充为空，不能把它当成本例原因。

## 5. 核心回复协议候选文本

以下是供评审的候选，不直接替换运行时代码。命令、questions 和具体工具的现有格式定义继续保留。

```text
【职责】
协助用户完成当前目标。按需直接回答、查询资料或使用当前可用工具；以实际结果为依据推进。

【回复协议】
软件通过回复格式识别下一步。是否使用工具，只决定处理方式，不改变任务结束格式。

1. 当前目标已满足且必要结果已核对：回复第一行必须单独、原样写【任务完成】，从下一行开始给出答案或交付结果。
2. 还需要工具结果才能完成：按当前工具说明输出对应请求，等待回传后继续处理。
3. 缺少影响目标的关键用户信息或授权：按 questions 格式提问，得到回答后继续原任务。
4. 正在等待必要结果，或操作结果尚未确认：保持任务未完成，按真实状态继续核实。

普通问答、解释、翻译、总结、写作和检索回答，完整答复当前请求时，也必须使用第 1 种格式；不需要为获得完成资格而调用工具。
目标尚未满足时不用完成格式。工具请求或 questions 所在回复不混入完成标记。
最终回答直接呈现用户需要的内容；除非用户询问，不解释本协议，也不以“已经回答过了”为由省略结束信号。
```

普通问答的正例：

```text
用户：把 good morning 翻译成中文。
助手：
【任务完成】
早上好。
```

工具结果已核对后的正例：

```text
用户目标：列出当前目录里的文件。
软件已经回传：README.md、package.json。
助手：
【任务完成】
当前目录有 README.md 和 package.json。
```

“软件已经回传”是示例前提，不可据此在真实任务中编造工具结果。以上独立行标记只有在分段器兼容后才能加入真实前缀。

建议的每轮短版：

```text
【回复约定】目标已满足时，首行原样写【任务完成】，下一行给出答案；普通问答也适用。还需工具、用户回答或必要结果时，按对应协议继续，不标记完成。
```

短版应放在程序生成的协议前缀中，紧邻真实用户正文。不能直接拼进用户正文尾部，否则会污染目标、专注视图显示、编辑匹配与本地消息记录。启用范围随提示词注入开关，不影响关闭注入时的原始发送。

## 6. 注入与运行时的配套设计

1. 把固定回复协议拆成可独立构建的内容；不同输出路径读取同一来源，预览、完整前缀和短版保持一致。
2. 环境/工具的 `full/delta/reminder/none` 账本继续保留。对每条真实用户发送单独计算是否需要短版，不用“原任务是否结束”作为唯一条件。
3. 确认普通发送、专注发送、附件说明、编辑重发、定时任务与澄清回答的适用范围；纯工具结果回传是原任务数据，不伪装为新用户目标。
4. 将协议文本放在用户正文边界之前，保持 `userTextOf`、`cleanFocusUserText`、目标原文、编辑请求确认和注入长度对账一致。完整前缀已含短版时避免重复。
5. 记录协议版本、实际发送的协议形式/字符数、回复是否带首行标记及当时是否存在未决状态；日志不写消息正文或敏感输出。
6. 漏标记先产生诊断和下一次发送的提醒依据；阶段性说明、等待、失败、截断不能一概记为违约，更不能仅因模型停止生成就结束任务。
7. 首轮不增加自动补发“请补完成标记”的模型请求；先对比提示词方案。自动纠偏若后续需要，应单独设计次数上限、原任务绑定和防重复机制。

## 7. 对比评估方案

由用户运行真实页面场景，智能体读取日志；本轮未执行测试、未启动 Electron、未调用真实页面，也没有新增或修改 `tools/` 下的探针。

先使用下面十类场景筛查现版本和候选版本。每类重复三次只是一个起步样本，不能据此声称达到统计意义上的百分之百可靠。

| 场景 | 应有行为 | 需要排除的退化 |
| --- | --- | --- |
| 名称解释、日常知识问答 | 完整答案首行带标记 | 为结束任务而启动终端 |
| 翻译、短文总结 | 给出结果并带标记 | 只给结果、漏结束信号 |
| 网页检索后的综合回答 | 必要检索结束后带标记，保留资料出处 | 检索未结束就宣告完成 |
| 连续追问与换题 | 回答当前请求；每条适用用户消息实际获得短版 | 前次漏标记导致后续规则一直缺席 |
| 终端/文件工具任务 | 工具请求与最终回答分开；结果核对后才结束 | 一边请求工具一边结束 |
| 关键目标不明确 | questions 提问，不结束 | 自行猜测并标记完成 |
| 后台任务尚未回传 | 等待必要结果 | 把创建成功当成全部完成 |
| 执行失败、结果未知、生成截断 | 保留真实状态，继续核实或请求必要介入 | 为满足格式而虚报完成 |
| 多轮长对话、增量更新与用户补充 | 完成格式保持；新增环境与工具信息生效 | 只在新对话有效，旧对话反复漏报 |
| 用户/资料正文引用完成标记 | 只有真实当前助手最终回复的首行能触发结束 | 引用、历史回复或资料内容触发结束 |

固定记录五项指标：目标确已完成时的首行标记命中率、目标未完成时的误结束率、工具请求格式正确率、不必要调用/重复执行次数、每条实际注入字符数。必要时再记录用户是否需要追问补标记。

先比较“文案与示例”版本，再比较“文案与示例 + 每轮短版”，以便区分文本和注入时机各自的贡献。使用同一平台/模型/模式，覆盖新对话和已有长对话；其他平台分别复核，不直接套用 DeepSeek 的结果。

离线回归重点是协议结构、示例分段、各注入模式、正文隔离、长度对账、历史兼容和完成识别。完成标记本身应精确断言；普通提示词措辞和自然语言答案不宜靠整段旧文案匹配评价正确性。

## 8. 推荐实施顺序

- P0：重写固定回复协议，增加普通回答正例，解决示例分段兼容；让任务路由只负责选方法。
- P0：将每轮短约定与完整环境/工具注入解耦，覆盖本例中“任务未结束所以不再提醒”的发送路径。
- P1：补齐缺标记的诊断和按状态判定的提醒条件，明确哪些情况不能自动结束。
- P1：按上述场景对比，确认改进没有带来误结束、额外工具调用或正文污染，再扩大到其他平台。

评审重点是规则是否无歧义、注入是否实际发生、完成与未完成是否都能正确处理；提示词字符数作为成本约束，不作为唯一优化目标。

## 9. 实施记录

- 固定回复协议、短约定和协议版本集中在 `src/shared/types.ts`；保持 `【任务完成】` 首行格式，并明确普通问答、工具请求、questions 和等待结果各自的处理方式。增加翻译和已确认目录结果两个正例，示例不代表当前任务事实。
- 完整提示词直接包含固定协议。主进程给增量/锚点计划补短约定，并按实际前缀长度提交账本；已注入任务中的后续用户消息只带短约定，另计上下文字符，不冒充环境/工具已重新注入。
- 原始输入框、专注文本、编辑重发、附件说明、定时任务和协议问答后的用户回答共用注入选择逻辑。短约定位于用户文本边界之前。关闭注入时两种协议均不发送，纯工具结果和原生交互卡片的提交保持原有路径。
- 分段器识别反引号和波浪号围栏，示例中的独立完成标记不会切成新章节。定时任务的历史提示词识别兼容旧角色文案和新角色/工具目录。
- 提示词日志增加协议版本、完整/短版、协议字符数。当前页面、当前任务且注入启用时，已稳定的普通回复漏标记会留下 `reply-without-completion` 记录；该事件只表示未收到结束信号，不认定违规、不重置任务、不自动补发消息。
- 新增/扩展分段、真实计划长度、各发送入口、旧边界兼容、关闭开关和诊断过滤用例。遵守仓库分工，智能体不运行测试；由用户运行回归和真实会话场景，智能体读取结果。
