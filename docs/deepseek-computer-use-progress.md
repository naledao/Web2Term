# 第 34 项：无进展检测与超时控制

本项把无进展信号、重复派发拦截和运行预算接入现有 TaskCoordinator／TaskProgression。信号出现后仍由 DeepSeek 根据实际结果诊断并换路径；达到硬上限后，客户端拒绝继续自动派发并保存未完成原因。现有系统提示词、助手角色、工具请求 JSON 和自动／手动确认规则保持原样。

## 可配置上限

computer use 设置中新增“运行上限”，设置保存到 SQLite。整个设置对象在写入前严格校验整数、字段和范围；损坏的历史设置使用有界默认值，不解释为无限制。新目标保存一份限额快照，后续修改设置不会静默扩大正在运行目标的预算。

| 项目 | 默认值 | 可配置范围 | 计算方式 |
| --- | --- | --- | --- |
| 任务时限 | 60 分钟 | 1 分钟—24 小时 | 当前目标的未暂停时间，包含模型回复、排队和交付等待 |
| 单步执行时限 | 120 秒 | 1—120 秒 | 进入 computer 执行器后开始；关联本机命令也按剩余预算约束 |
| 条件等待时限 | 3600 秒 | 1—3600 秒 | wait_for 使用独立预算；原动作／helper 自身较短的期限仍有效 |
| 任务步骤上限 | 200 步 | 5—2000 步 | computer 动作、协议／拦截反馈及同任务 command／read_files 的新步骤 |
| 同一动作无进展上限 | 4 次 | 2—20 次 | 自最近实际证据变化以来，同一语义动作的请求次数 |
| 同来源相同观察提示阈值 | 6 次 | 2—50 次 | 对同一来源连续得到相同状态时提示，无单独硬停止 |
| 连续执行故障超时上限 | 3 次 | 1—20 次 | 动作/执行器/helper实际超时；正常条件wait_timeout单列信号 |
| 一次诊断恢复上限 | 12 步 | 2—100 步 | 失败／无进展进入诊断后，尚未取得新证据时的接续步骤 |

设置以毫秒和整数次数持久化，界面按分钟／秒／次数显示。任务剩余时长、单步时限和原工具自身时限取更紧的约束；客户端不通过增大 helper 期限延长一个原本更短的动作。

## 语义动作指纹与派发前拦截

每次接纳新 computer 请求时，对动作名称、目标和参数生成 SHA-256 指纹。步骤令牌、消息传输编号和 observation_id 不参与“取得进展”的判定。控件重新编号时，尽可能使用最近真实控件的角色、名称、位置和状态形成的散列；窗口通过已有完整身份索引关联，应用通过已发现的可执行路径／名称关联，启动引用刷新不自动成为新的启动意图。

相同点击、提交、输入和启动动作在没有新证据时再次请求，返回no_progress／not_executed。滚动、已知窗口激活及受控导航键允许有限重复，仍受同动作上限约束；Enter等提交键不享受导航豁免。模型可以先观察核对后状态、调整方法或选择其他实际可用工具。继续请求达到重复上限时，回传 progress_limit 并停止该目标的后续自动推进。

只读发现、观察、交互查询、复核和条件等待不因重复次数或相同状态单独硬停止，仍受任务步骤、实际恢复预算和总时限约束。相同观察按连续同来源计数，仅提供提示。有效新观察即使内容未变，也能结束相应的诊断恢复；部分UIA本身不是执行故障。现有接纳去重仍先执行：重复报告同一回答或旧令牌不会消费新的运行预算。

指纹不授权操作，不替代窗口／观察有效期、任务代次、主进程参数校验或桌面运行凭据。它只识别请求之间的联系；不同参数也不能绕过任务总步骤和恢复上限。

## 可观察状态摘要

进展判定只读取真实执行器结果，不把新 UUID、时间戳、令牌、模型自述或交付成功当成状态变化。摘要使用：

- 图像内容 SHA-256、窗口完整身份、来源／裁剪位置、控件角色、名称、边界及可用／焦点状态。
- 应用／窗口列表中的稳定属性和真实状态，排除每次刷新生成的引用及采样时间；列表顺序规范化。
- 当前文件步骤成功准备的源文件路径、字节数和内容 SHA-256。历史文件索引在后续其他步骤中重复出现，不会再次重置恢复计数。

只保存有界散列与计数：最多 64 个动作指纹、32 个来源摘要、200 个最近控件的编号／散列映射。不会把控件正文、输入文字、截图字节或命令正文复制进运行控制状态。

实际证据变化会开始新的观察阶段，并结束上一轮无进展／诊断计数。部分控件树仍按第 33 项处理，不能据此断言未列出的控件不存在。动作执行成功或命令退出码 0 本身不构成业务进展；该目标是否完成仍需第 35 项的实际结果验证。

本项检测的是可观察变化，不声称理解所有业务语义。页面时钟、动画或同一来源中来回切换的内容可能形成图像变化，所以任务总步骤、恢复预算和总时限继续作为独立硬约束。

## 超时与执行器退场

任务时限使用当前进程的单调时钟及单个可取消期限，不通过轮询模型或截图计时。暂停、等待模型提问的用户回答期间停止累计，恢复后只使用剩余预算。模型生成中、工具排队和结果交付等待仍占用总任务时长，但不增加动作重复、观察或超时次数。

computer 单步期限从取得运行机会、真正进入执行器时开始。超过期限时，对该步独立执行信号发出取消请求，结果交付信号不因此立即作废。继续等待真实执行器返回及原有 helper 监督／退场屏障，才释放桌面运行凭据，不用 Promise.race 提前释放一个可能仍在输入的执行器。

Windows helper 沿用已有取消、500ms 退场监督及硬期限。输入／截图适配层保留实际 helper_code，以便区分原生 action_timeout。若执行器无视取消，任务总期限仍能停止该目标的后续推进，运行凭据继续等待实际退场，不承诺期限到达的同一毫秒已经停止所有原生副作用。

期限过后仍取得实际 executed／成功回执时，保留原 ok、code 和执行事实，用 progress_control.action_timed_out 记录超时事件；不能把真实成功改成“未执行”。可能已经生效且缺少有效后观察的动作，继续触发第 32—33 项的新 observe 门槛，不自动重做输入。

同任务本机命令在实际执行前取单步／任务剩余预算，缩短原 shell 期限；未关联任务的命令保持原有规则。文件读取继续使用原信号与任务归属取消。已经运行的后台任务沿用原监控和真实进程状态，本项不因超时自动重启，也不把它们假定为已经退出。

## 诊断、交付与停止

computer_result.progress_control 包含累计步骤、已用时间、重复动作、相同观察、连续超时和恢复计数，以及 signals、halted、stop_reason、guidance、goal_verified=false。第 33 项诊断支持 no_progress／progress_limit，并在达到硬上限时不再建议继续自动重试。

结果触发上限时，实际动作回执、控制状态和原因一起保存，沿原通道尝试交付最后一份结果；交付确认后步骤进入 blocked，不激活下一枚输入令牌。任务期限或派发前已耗尽的总预算会直接停止目标、取消后续派发，可能在途的执行／提交按原规则保留未知状态及迟到事实。

交付 busy／no-composer 和已确认未提交的重试复用原正文，不重新计算指纹、不重复动作或观察，也不增加执行／恢复计数。总任务时限仍约束长期交付等待；提交未知继续停止重发。

任务概况显示预算及明确停止原因，固定保留未完成状态。达到上限后的目标不能由迟到的页面“完成”消息触发任务完成通知。已保存的目标、输入、资源、已执行步骤、未知事实和产物线索继续保留，不撤销或虚构回滚。

## 恢复与版本兼容

控制状态可随任务 payload 持久化并经过严格结构校验；旧任务仍可读取，首次接入预算时保留已知步骤数。正常恢复沿用原目标限额、已用时间和计数，并重新观察；不恢复旧执行凭据、定时器或待派发动作。崩溃后的已用时间以最近实际保存的进程计时为准，不把重启期间的时间猜测为工作时间。

动作结果已经保存、任务检查点更新失败时，启动恢复按原任务／代次／步骤核对最后一份真实回执，补回已知计数和硬上限原因，不能因此清零预算或重新激活任务。后续总时限清理仍保留最早的硬上限原因。

已经达到硬上限的任务不通过“恢复原任务”清零预算。用户可调整设置后重新提交一个目标，原任务的未完成历史保留。界面不会自动增大上限或新建目标规避限制。

完整业务完成与产物验证仍属于第 35 项；完整暂停／恢复交互仍属于第 36 项。本项沿用现有暂停控制，仅补齐其预算计时。
