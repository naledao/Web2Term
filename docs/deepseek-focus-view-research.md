## 二、Codex 官方资料支持的交互原则

官方 App Server 将一轮工作、轮内消息与工具活动分开，提供独立的生命周期及输出增量；这是采用“用户一轮 → 若干内部步骤 → 最终答复”模型的依据。[App Server 事件文档](https://learn.chatgpt.com/docs/app-server#events)

官方集成终端按当前聊天的项目或 worktree 提供单独入口，支持在聊天旁查看命令输出。可据此将本项目终端收进按需展开的面板。[集成终端](https://learn.chatgpt.com/docs/integrated-terminal)

官方代码审查面板用于检查变更和行内反馈。对应到本项目，可让文件变化和执行输出进入详情区域，主对话保留结果说明。[代码审查](https://learn.chatgpt.com/docs/code-review?surface=app#review-local-changes)

官方提示指南建议用简短进度说明帮助用户理解工作，不让对话变成工具调用日志。[Codex 提示指南](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide)

这些资料可确认事件结构和交互分工，不能证明当前桌面客户端每一处像素、折叠规则或动画。本设计中的“已工作 N 秒”“查看过程”等细节是针对本项目提出的方案。

## 三、默认隐藏的内容与保留的反馈

| 当前内容 | 专注视图默认表现 | 详情位置 |
| --- | --- | --- |
| 助手的 command / read_files 协议 JSON | 不作为正文显示 | 本轮步骤 → 命令详情 |
| 软件自动发出的“上一条命令执行结果” | 不作为用户消息显示 | 对应步骤 → 输出/回传状态 |
| 注入提示词及协议标记 | 不进入主对话正文 | 执行设置或诊断信息 |
| 重复的命令—结果—下一条命令 | 合并为同一轮处理过程 | 按时间排序的步骤 |
| 完整终端滚屏 | 默认收起 | 顶部“终端”入口 |
| 右侧执行控制与统计 | 默认收起 | 顶部“执行设置”入口 |
| 普通进度说明 | 仅显示简短、与当前动作对应的说明 | 点击展开相关步骤 |
| 需要用户确认的问题或命令 | 在主对话内显示可操作卡片 | 同时关联本轮详情 |
| 命令失败、连接断开、回传失败 | 显示明确状态和恢复操作 | 展开后可看完整输出 |
| 最终回答、真实用户消息和附件 | 正常展示 | 可复制与选区追问 |

隐藏是展示层归并。实际命令仍走现有执行器、幂等和确认流程，原网页仍保留全部真实会话。模型标签仍为 DeepSeek，不声称已接入真正的 Codex 服务。

## 四、专注布局

左侧保留当前会话和项目导航，中间成为完整聊天区域。顶部只保留会话名、模型、原网页、终端、执行设置和主题入口。终端和设置在右侧抽屉中按需展开，不默认挤占聊天区。

每次用户提问下面是一条连续的助手回复：

- 工作中：一条简短进度，例如“正在检查页面结构…”；可展开本轮的思考、搜索、文件读取与命令步骤。
- 工作结束：显示“处理用时 12 秒 · 3 个步骤”，过程默认收起，随后展示最终回答。
- 等待确认：在正文显示待运行命令的目的、实际命令、目录及确认/拒绝入口；不能隐藏后导致任务无反馈地等待。
- 失败或中断：保留部分回答和输出，主区域显示状态；不把失败卡收进默认关闭的细节中。
- 内部回传期间：可以简短显示“正在整理执行结果”，不插入新的用户消息气泡。

输入区常驻底部。生成期间可停止，草稿保留；中文输入法回车只选字，Shift+Enter 换行。阅读历史时保持滚动位置，新内容通过“回到最新消息”提示。

本地原型中可以切换“显示内部消息”对照封装效果，展开工作过程、查看命令输出、播放模拟流程、观察确认与失败状态、打开终端面板和切换主题。该对照开关属于设计预览工具，不作为最终产品的常驻入口。

## 六、还需要补齐的核心

1. 增加工作轮次与有序步骤。一个真实用户发送建立 turnId；后续多次内部命令和回传使用同一 turnId。原有 taskStartedAt 可能跨越多次人类追问，不能直接充当每次提问的轮次 ID。
2. 增加明确来源与关联：human、assistant、internal-result 等，关联执行 messageId。对用户正常发送的“上一条命令执行结果”文字照常展示，不能按前缀一刀切隐藏。
3. 生产视图读取全部可见思考/搜索片段以及流式正文；新增展示事件，不修改现有命令扫描器的输入 DOM。思考与正文都只取网页已提供的内容。
4. 将执行完成和回传完成分开。现有 Shell 执行流程已经区分结果，但 shell 的成功回传仍需可持久化的结构化状态，不能只依赖终端文字。退出码 0 不等于模型已收到输出。
5. 确认工作结束：模型回复结束、命令和回传均无待处理项，且没有待答问题。单纯网页静止、停止图标消失或 command done 不能单独成为整轮完成依据。
6. 处理旧历史：没有可靠轮次关联的旧记录按已有历史展示，不根据邻近时间伪造步骤归属；不自动隐藏来源不明的记录。
7. 保留选区追问。当前 QuestionChatPanel 可见性依赖 nativeEmbedVisible，隐藏网页会取消网页选区；封装视图需要从 renderer 选区调用同一上下文服务，并单独管理侧边聊天可见性。
8. 提供原网页恢复入口。登录、验证码、未知页面结构和状态待确认时，用户可切回实际页面；不在隐藏状态下反复重新登录或重发。

建议的数据结构是“轮次 + 有序项目”，项目包含用户可见说明、可见思考、搜索、文件读取、命令、回传状态、提问和最终答复。轮次身份由应用产生，并绑定 sessionId / platformId / conversationId；虚拟行号只用于瞬时定位。

## 七、实现路径比较

| 路径 | 隐藏内部消息的可靠性 | 评估 |
| --- | --- | --- |
| 给 DeepSeek 页面注入 CSS，隐藏部分 DOM | 容易受虚拟列表和站点改版影响，原扫描及选区也依赖这些节点 | 不作为主要方案 |
| 扩展现有干净对话视图，后台保留原网页 | 可用真实消息来源和执行记录来归并，展示由项目控制 | 推荐先做 |
| 改为接入 Codex App Server 或另一套模型 API | 能获得更完整的结构化事件，但需要改变模型和接入路径 | 当前目标不要求迁移 |

先完成专注布局、已存消息和真实执行状态的汇总，再补齐流式过程、输入发送、停止、附件、选区追问和恢复路径。生产实现需由用户通过 npm run dev 做真实会话验收。
