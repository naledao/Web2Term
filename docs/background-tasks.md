# 后台任务

后台任务登记成功后，右侧自动打开并选中「后台任务」页签；侧栏折叠时会展开。右侧「＋」菜单也提供该入口。关闭页签不终止任务或停止日志观察；日志、状态和通知发送进度更新不会反复抢占当前页签，下一次新建任务时才再次打开。

## 软件启动与历史登记兼容

新任务通过 command JSON 的 `background:true` 请求后台执行，`command` 只填写实际任务命令。软件负责启动进程、生成日志及退出码文件并登记监控，模型不再编写登记脚本。

旧启动脚本的以下输出仍兼容识别；此登记格式只保留在实现文档中，不再进入工具提示词：

```text
__W2T_BACKGROUND_TASK__{"pid":12345,"name":"开发服务","log_path":"/absolute/path/service.log","stderr_path":"/absolute/path/service.err","exit_code_path":"/absolute/path/service.exit"}
```

- PID 必须来自本次实际启动的进程；12345 只是格式示例。
- `name` 和 `log_path` 必填；日志路径必须是执行机器上的绝对路径。
- `stderr_path` 可选。stdout/stderr 合并时只提供 `log_path`；Windows 的 Start-Process 分别重定向到两个日志文件。
- `exit_code_path` 可选。后台任务结束后向该文件写入整数退出码，软件才能区分完成和失败。进程消失但没有退出码时显示「已结束」，不会当作成功。
- 每次新启动使用独立日志和退出码文件，日志采用 UTF-8。
- 启动命令打印登记行后返回；后台任务必须脱离当前终端生命周期。
- 标准输出格式中，标记与 JSON 位于同一行。兼容两次 `Write-Output` 形成的「标记独占一行、下一行紧跟完整紧凑 JSON」；不会跨过空行或普通日志寻找 JSON，也不会拼接不完整的 JSON。
- 只解析实际执行结果中的完整登记行，不从模型聊天文字或旧的执行历史自动登记。

任务绑定执行启动命令时的本机、SSH 主机或 Web2Term 设备。观察使用独立 Shell，不占用模型的主终端。约每 4 秒读取一次状态和日志；同一目标的读取串行执行，文件未变化时仅返回元数据。断线或切换设备后显示「状态未知」，恢复原连接后重试。进程启动标识变化时将原任务视为已结束，防止 PID 复用。

运行中任务的卡片右侧和详情页提供「停止」。点击后显示「停止中…」，软件在任务原目标上核对进程启动标识，停止该进程及其子进程；停止操作与日志观察共用串行通道。确认退出后显示「已停止」，移入已结束列表并保留日志。连接断开、身份无法核对或权限不足时显示原因。该操作只针对所选后台任务。

## 等待与自动回传

后台任务区分一次性任务与常驻服务。新命令使用 `background:true`，并可通过 `background_kind:"job"` 明确等待退出，或通过 `background_kind:"service"` 等待启动就绪。任务类型与就绪配置保存在执行记录中，历史重放也保留这些条件。

常驻服务示例（命令替换为项目实际启动命令）：

```json
{"command":"dotnet run --no-launch-profile","description":"启动后端开发服务","background":true,"background_kind":"service","readiness":{"type":"auto","timeout_seconds":120},"timeout_seconds":30}
```

- `auto` 识别 ASP.NET Core、Vite 的明确启动完成日志和服务地址，并核对监听端口属于登记进程或其子进程。启动日志按偏移增量读取，每次每路最多 128 KiB，与界面显示的日志末尾独立；已取得的证据和读取偏移会保存。
- 已知端口可设置 `readiness:{"type":"tcp","port":44301,"timeout_seconds":120}`。软件确认该端口由本任务进程树监听；旧服务占用同一端口不能使新任务通过。
- 项目已有健康接口时可设置 `readiness:{"type":"http","url":"https://localhost:44301/health","timeout_seconds":120}`。软件在端口归属确认后要求指定接口返回 2xx；不跟随重定向，不跳过证书检查，不臆造健康接口。地址仅允许目标机器的回环地址，SSH/Web2Term 检查也在任务原机器执行。
- `timeout_seconds` 外层仍只限制启动器，最多 30 秒。就绪等待默认 120 秒，可配置 10～600 秒。就绪超时只通知“进程仍运行但就绪未确认”，不终止或重启进程；继续观察后若就绪会再通知成功。**常驻服务运行没有总时长上限。**
- 就绪后显示“已就绪 · 运行中”，继续监控并保留停止入口。顶部按启动中、运行中和已结束计数。没有新字段的旧记录可以根据明确的开发命令或启动日志识别服务；明确标记 `job` 的任务始终等待退出。

登记成功后，软件保留启动命令的执行记录，向原平台、原对话发送一次「【后台任务已创建】」，包含任务名、PID 和日志路径。消息明确说明已由软件接管监控、创建成功不代表任务完成，要求模型简短确认后等待，不再发送轮询命令。软件独立等待任务结束，再多读取一次最终日志，然后发送一次「【后台任务执行结果】」，包含状态、退出码、日志路径和有长度限制的 stdout/stderr。手动停止的结果会明确要求模型等待用户，不自动重启、重试或修复该任务。普通启动输出不另外发送。

常驻服务满足就绪条件后发送一次「【后台服务已就绪】」，包含地址、确认依据和继续原任务的指示。就绪只完成启动步骤，不会结束进程或直接宣布整轮任务完成。快速启动时将未发送的创建确认合并到就绪通知；就绪通知排队期间进程已退出、手动停止或任务被取消时，不发送过期的可用状态。一次性任务仍保留创建确认与结束结果的顺序。

页面正在生成、存在文字或附件草稿、正在等待用户回答、自动化已暂停、终端模式关闭，或者对话、执行主机已切换时，各类通知分别排队。恢复原对话和执行目标且页面空闲后继续尝试。通知按任务与事件独立去重。提交结果不确定时停止自动重试，在后台任务页显示需要处理的提示。用户主动结束任务会持久化取消该轮任务的后续自动回传，观察记录和后台进程仍保留。

基础系统提示词的「执行方式」保留简短的选择规则：预计超过 2 分钟、持续输出、等待外部事件或需要脱离当前终端运行的非交互任务，使用 `background_task`；短时、一次性命令直接执行。后台任务的具体启动、登记格式和等待约定位于「查看工具提示词」的 `background_task` 工具说明中。Web2Term 也启用后台任务工具说明，同时继续关闭不支持的 `read_files` 工具。

工具提示词只保留调用方式、`job/service` 区分、就绪参数、两类超时和等待约束，并提供一个常驻服务 JSON 示例。PID、日志文件、端口归属校验、通知合并和历史登记兼容等实现细节保留在代码与本文档；创建、就绪、超时和停止后的具体行动由对应回传消息说明。使用时机保留在系统提示词。工具提示词约 600 字符，回归断言限制在 650 字符以内，避免继续堆叠实现说明。这个分工参考 [OpenAI 工具描述建议](https://developers.openai.com/api/docs/guides/function-calling#best-practices-for-defining-functions)中对调用时机、参数格式与返回含义的要求，以及[提示词编写建议](https://developers.openai.com/api/docs/guides/prompt-generation)中清晰、具体、删去不必要指令的原则。

## 当前范围

- 任务记录按工作区保存在本地数据库（`background_tasks` 表），重启应用后恢复列表；删除工作区时一并删除。每个工作区保留最近 50 条，运行中或仍有通知未送达的任务不会被清理。
- 重启后，运行中的任务继续观察：本机任务立即恢复；SSH/Web2Term 任务在本工作区重新连上同一主机或设备后继续读取，此前显示「状态未知」。保存的进程启动标识仍用于识别 PID 复用。重启期间已经结束的任务，重启后读到结果并照常回传。
- 重启前尚未送达的创建、就绪、就绪超时和结束通知重新排队，回到原对话、执行目标一致且页面空闲时补发；已发送、已取消、被更新状态接替或需要手动处理的通知不再重发。提交通知前先保存发送中状态；若应用在提交过程中退出，重启后标为结果未确认，要求核对原对话，不自动重复提交。
- 运行中的任务只保存状态，不保存日志内容（重启后从日志文件重新读取）；已结束的任务保存最终输出，供补发结果使用。
- 关闭应用只释放观察通道；脱离终端的后台进程及日志文件由其自身生命周期决定。
- 页面分别展示 stdout/stderr 的最新 64 KiB，超出时提示截断；完整输出仍在日志文件里。支持跟随输出和手动滚动阅读。
- 已结束的任务收进可展开的历史列表，详情页保留日志。
- Web2Term 的独立观察通道占用一个设备终端名额；设备已有 3 个活动终端时，会显示通道不可用原因，释放名额后自动重试。同一工作区内的多个后台任务共用观察通道。
- 一次性任务发送创建确认和最终结果；常驻服务增加一次就绪结果，就绪后 AI 可以继续后续工作。运行日志只在后台任务页更新，不持续向模型发送，也不需要模型轮询。后台进程可通过卡片或详情中的「停止」手动终止。

## 由用户运行的检查

离线回归（假 Shell、假定时器，不启动 Electron 或真实进程）：

```powershell
node --test tests/background-tasks.test.mjs
node --test tests/background-task-stop.test.mjs
node --test tests/background-readiness.test.mjs
node --test tests/background-execution-storage.test.mjs
node --test tests/background-task-results.test.mjs
node --test tests/background-task-panel.test.mjs
node --test tests/recent-command-run.test.mjs
```

本机 Shell 的日志读取检查（临时文件和测试进程自己的 PID，不启动 Electron、不连接网络）：

```powershell
node --test tests/background-task-shell.test.mjs
```

交互检查通过项目约定命令启动：

```powershell
npm run dev
```

建议开始一轮新任务，让模型执行一个明确允许放后台的短任务，例如「启动一个一次性后台任务，每秒输出一行，共输出 20 行；使用 background:true、background_kind:"job"，结束后由软件自动回传结果」。检查：

1. 默认页签栏没有「后台任务」，「＋」菜单内有该入口。
2. 页签未打开时启动任务，自动打开并切换到「后台任务」，折叠侧栏时也会展开，列表能看到任务和真实 PID。
3. 点击任务能看到日志追加；标准输出、错误输出分别可查。查看日志时主终端仍能执行其他命令。
4. 从「＋」重复点击只选中已有页签；关闭再打开能继续查看同一任务。
5. 有退出码文件的成功／失败任务显示相应状态；没有退出码文件的进程退出显示「已结束」。
6. 多任务的日志相互独立；本机和 SSH/Web2Term 各检查一次。切换主机后旧任务显示未知状态，恢复原连接后继续读取。
7. 登记成功后，原对话自动收到一次「后台任务已创建」，模型只简短确认并等待。结束并读取最终日志后，再收到一次「后台任务执行结果」，包含最后输出和真实退出码。运行期间不重复发送状态通知；用户关闭页签后日志刷新不把它重新打开。
8. 运行中或排队时暂停，或者在网页输入框保留草稿；完成结果等待，不覆盖草稿。恢复并清空草稿后自动发送。切到其他对话不会收到原任务的结果，回到原对话后继续发送。
9. 手动结束任务后，即使后台进程稍后退出，也不重新唤醒 AI。关闭后台任务页签则仍保留监控和自动回传。
10. 任务运行中关闭并重新启动应用：列表恢复，任务继续观察并在结束后回传一次结果；在任务结束后、结果送达前重启，重启后补发且只发一次。重启前已结束的任务以历史形式出现。
11. 基础系统提示词包含何时使用后台任务的「执行方式」规则，不包含登记字段和协议示例；工具提示词显示精简的 `background_task` 约定及一个常驻服务 command JSON 示例，不包含历史登记行或虚构的端口、健康接口。

本功能的交付标准为「构建通过，等待测试」。上述离线回归和交互检查由用户执行。

## DeepSeek computer use 的后台依赖（第 25 项）

启用本机 computer use 后，真实目标创建的后台任务会保存原启动步骤和机器关联。模型可先执行独立工作，依赖服务或后台产物时使用 `computer.wait_for` 的 `background_ready`／`background_finished` 条件及通知中的 `background_id`。等待直接接收既有监控状态发布，不增加进程或日志轮询。退出成功需原监控完成最终日志回读且退出码为 0；业务产物仍需后续工具核对。

带目标关联的后台通知与当前工具结果发送互斥；显式等待已取得的里程碑通过 computer 结果回传，避免再发送重复通知。换目标会取消旧等待及其自动通知；重启可恢复进程观察，但已中断目标的等待和执行授权不会恢复。没有目标关联的旧任务继续按本文件原规则恢复通知。软件后台启动器对同目标、同机器／目录、同命令和配置的未结束任务返回原引用，不重复启动；手动停止记录阻止自动重启。

参数、取消／重启边界与由用户运行的测试见 [第 25 项实现说明](deepseek-computer-use-background-wait.md)。
