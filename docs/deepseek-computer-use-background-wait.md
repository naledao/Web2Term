# 第 25 项：后台任务依赖与业务等待

用户布置一个目标后，模型可以先创建后台任务，再完成与它无关的工作；当下一步依赖后台服务或生成结果时，使用现有 `computer.wait_for` 等待真实状态。软件复用后台任务监控，在条件满足、失败、停止或超时时返回一次工具结果，由当前 DeepSeek 模型选择下一步。

现有系统提示词、助手角色、终端／文件／后台启动工具的 JSON 协议、自动／手动执行和确认规则保持原样。新增内容限于 computer 的动作参数、后台结果元数据和主进程任务关联。没有独立规划器，也没有新的后台启动通道。

## 等待条件

| 条件 | 参数与期限 | 满足依据 | 未满足时的结果 |
| --- | --- | --- | --- |
| `background_ready` | `background_id` 必填；`timeout_ms` 默认 600000，范围 100—3600000 毫秒 | 原任务已有服务就绪监控；监控确认原进程仍运行，且就绪状态与 `readyAt` 证据成立 | 服务就绪超时、进程结束、停止或等待超时均不能作为就绪；一次性 job 使用此条件会被拒绝 |
| `background_finished` | 相同参数与期限 | 原监控确认进程结束，完成退出后的最终日志回读，状态为 completed 且退出码为 0 | 非零退出码为 failed；未知退出码为 unconfirmed；手动停止为 cancelled；仍在运行或未知状态继续等待至期限 |

后台条件只接受 `condition`、`background_id` 和可选 `timeout_ms`，不接受 PID、窗口筛选、观察引用、脚本、正则、日志路径或截图参数。原有三个桌面等待条件的默认 10 秒和最长 30 秒限制仍由独立校验保留。

`background_id` 从本目标真实后台通知取得，不使用名称推断目标。示例中的 ID 和令牌仅展示格式，调用时须替换为真实结果及当前令牌：

```json
{
  "type": "computer",
  "version": 1,
  "action": "wait_for",
  "step_token": "<当前有效步骤令牌>",
  "condition": "background_finished",
  "background_id": "<本目标真实后台任务 UUID>",
  "timeout_ms": 600000
}
```

## 任务归属与依赖记录

后台登记保存启动命令的 `TaskToolContext`，包括目标、代次、会话、来源、启动步骤和机器。通知携带 `background_id` 与原启动 `task_context`。等待前由主进程再次核实当前 computer 步骤的来源、已消费令牌、本机机器和原启动任务归属；模型不能覆盖这些关联。

`AutonomousTask.backgroundDependencies` 保存后台 ID、启动步骤、等待步骤、机器、条件和等待结果，最多保留 64 条历史。保存成功后才开始等待。旧版本没有关联的后台记录仍沿用原监控与通知；关联损坏的记录保留显式无效状态，不能降级为无归属通知。

等待结果包含 `condition_met`、`wait_status`、`elapsed_ms`、后台实际状态、最终回读标记、退出码、服务证据、最后检查时间及有界日志。成功只表示指定依赖条件得到确认，`goal_verified` 始终为 false。报表内容、文件完整性、页面效果等业务验证仍需模型继续选择文件、终端或桌面工具完成。

## 调度、回传与重复启动

`TaskBackgroundWait` 接收既有 `BackgroundTasks` 的状态发布，使用一个可取消的期限定时器。它不新建观察进程、不增加进程／日志轮询，不调用原生 helper，不获取截图，也不发送中间模型请求。既有监控继续负责进程身份校验、服务就绪探测、日志更新和退出后的最终回读。

后台登记后，任务处于可选择下一工具的状态。模型可以先做独立工作；显式调用等待后，当前步骤保持执行中，直到收到真实结果。其他会话和其他后台进程继续使用原有调度。当前调用仍遵循首版本机 Windows x64、DeepSeek、已启用 computer 且动作可用的入口限制。

后台通知共用既有 `BackgroundTaskResults` 队列，并与当前目标的命令、文件和 computer 步骤发送互斥。通知发送期间，快速到达的下一请求和普通答复会暂存；明确发送成功后才释放。busy／no-composer 仅等待再次交付，提交未知则标记需要处理并阻塞该目标，避免重复发送或继续执行未确认的后续动作。

显式等待已取得的里程碑，通过普通 computer 结果发送，对应后台通知标记为 superseded。服务就绪等待合并创建、就绪与过期的就绪超时通知，服务将来退出仍可通知；最终结束等待合并已有创建／就绪／超时／结束通知。调用自身超时且后台仍未达到里程碑时，不消费将来的真实就绪或结束通知。所有入口的完整统一发送队列仍属于第 29 项。

同目标、同代次、同机器／目录下，软件后台启动器再次收到相同命令和配置时，会返回仍在观察的原任务引用，启动步骤标记为未执行，不再拉起进程。检查中、运行中、未知状态或尚在最终回读的任务均保留原引用；手动停止记录也阻止自动重启。确认结束的普通成功／失败任务允许模型按实际诊断决定后续修复。此去重针对软件管理的后台启动，不通过命令关键字猜测任意脚本的副作用。

## 取消与重启

停止、换目标、换会话、作用域变化或关闭会话时，等待移除期限定时器和取消监听，后续监控事件不能驱动旧步骤。换目标还会取消旧目标通知及其进行中的关联发送。取消等待不会终止或重启后台进程；进程仍按原后台监控与用户停止操作管理。

任务记录重启后作为中断历史读取，等待中的依赖标记为 cancelled，不恢复等待或执行授权。后台监控本身仍可恢复观察；带旧目标关联的通知不重新驱动已中断目标。发送中断后不自动重复提交。旧版本无目标关联的后台任务继续遵循原通知恢复规则。

## 构建与用户测试

交付标准为“构建通过，等待测试”。智能体不运行测试，不启动 Electron／helper，不执行真实后台任务或桌面操作。

用户可在仓库根目录运行离线合成用例：

```powershell
node --test tests/task-background-wait.test.mjs tests/task-tool-collaboration.test.mjs tests/background-task-results.test.mjs tests/background-tasks.test.mjs tests/background-readiness.test.mjs tests/windows-wait.test.mjs tests/windows-observation.test.mjs
```

这些用例使用合成后台状态、定时器、终端、回执与窗口信息，覆盖依赖记录、独立工作、服务就绪与最终回读、非零／未知退出码、手动停止、期限、越界归属、取消迟到结果、通知合并、重复启动和重启不恢复授权。

真实会话通过 `npm run dev` 启动，由用户检查：布置“后台生成文件，同时准备其他内容，生成结束后打开核对”的目标；确认登记不会直接报告整体完成，独立步骤能先推进，有依赖步骤会等到最终结果后继续。再检查服务就绪、失败、手动停止、草稿占用、暂停、换目标与重启场景。观察到等待结束不能代替核对实际文件和应用效果。
